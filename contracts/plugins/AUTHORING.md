# Посібник автора сервера каталогу

> Нормативний джерело полів — `../PROTOCOL.md` і `../openapi.yaml`.
> Цей файл — про **порядок робіт, рішення й пастки**. Як є сумнів у полі —
> дивись `openapi.yaml`, а не сюди.

---

## 1. Що ти насправді будуєш

Не «плагін». Сервер каталогу — це HTTP-сервіс, який відповідає на чотири питання:

```
GET /status     «як мене звати і що я вмію»
GET /search     «що я знайшов за цим запитом»
GET /details    «що я знаю про цей фільм»
GET /streams    «де дивитися цю серію»
```

Між цими ендпоїнтами — твої адаптери. Вони можуть скрейпити сайти, читати
 torrents, ходити в чужий API — байдуже. Kadrbox бачить тільки JSON.

**Найважливіше:** застосунок ніколи не виконує твій код. Він робить HTTP-запит.
Тому ти можеш писати на чому завгодно — і жодна зміна тут не вимагає
плагіна в застосунку.

---

## 2. Мінімум, з якого можна почати

Ти можеш мати один ендпоінт і вже бути корисним.

```ts
app.get('/status', () => ({
  protocol_version: 1,
  app: 'Мій каталог',
  capabilities: ['search'],
}));
```

`search` — єдиний обов'язковий крок. Решту додаєш, коли буде.

### Як перевірити, що тебе зрозуміли

```bash
curl -s https://твій-сервер/status | jq
```

Якщо бачиш `protocol_version: 1` — ти в нормі. Клієнт ніколи не впаде на
невідомій версії: він попередить і працюватиме далі.

---

## 3. `catalog_id` — необов'язковий

```json
{ "protocol_version": 1, "catalog_id": "my-catalog", "capabilities": [...] }
```

**Не віддавати `catalog_id` — це повністю коректно.** Контракт вимагає рівно
три поля: `protocol_version`, `app`, `capabilities`. `catalog_id` — необов'язкове
поле, і клієнт зобов'язаний прийняти його відсутність.

Навіщо він існує: `item_id` **не глобально унікальний**. Два різні сервери можуть
повернути однаковий `item_id` для різного контенту. Тому Kadrbox склеює ключ
`<catalog_id>:<item_id>` і зберігає історію, обране та завантаження саме так.
Якщо сервер не оголошує `catalog_id`, клієкт **сам** виводить ідентичність з
базової URL-адреси: `<host>-<sha256(url)[0:16]>`. Стабільно, різні сервери
отримують різні простори, і тобі не треба нічого зберігати.

Коли все ж варто віддати: тільки якщо в тебе є причина. Тоді два правила
обов'язкові:

- він має бути **стабільним** на весь життєвий цикл каталогу — значення, що
  змінюється при перезапуску, осиротить усю збережену в користувача історію;
- два різні сервери з однаковим `catalog_id` **зіллють** сховище. Це гірше, ніж
  не віддавати нічого.

І не вигадуй `catalog_id` з імені сайту-джерела (див. §16).

## 4. `segments[]` — обов'язково, навіть з одним джерелом

```json
"segments": [
  { "id": "src_a", "label": "Джерело A", "provider": "src_a",
    "status": "ok", "item_count": 12 }
]
```

`status` ∈ `ok | empty | error`. Обов'язковий. Коли ти робиш фан-аут на
кілька джерел, одне з них мертве — це норма, а не виняток.

**Найважливіше правило про помилки:** якщо джерело впало — поверни `200` з
`status: "error"` для нього, а **не** `502` на весь запит. І не викидай сегмент.
Клієнт показує стан по кожному й лишає решту працювати.

Виняток: якщо впало **все**, тоді `502` доречний.

---

## 5. `item_count` — рахуй, а не вигадуй

Скільки елементів у `items` належить цьому сегменту. Клієнт показує це як
«N з джерела X», і користувач помічає нестачу.

Якщо `status` не `ok` — `item_count` зобов'язаний бути `0`.

---

## 6. Епізоди та озвучки

Схема нижченасинхронно: сезони й серії приходять **в одній** відповіді `details`,
а не окремим запитом на кожен епізод. Екран, якому потрібно N запитів, ніхто не
чекає.

Два поля, які найчастіше роблять неправильно, тому розклав їх явно:

```json
{
  "item": { "id": "…", "provider": "…", "kind": "series", "title": "…" },

  "voiceovers": [
    { "id": "uk", "label": "Українська", "lang": "uk", "default": true },
    { "id": "en", "label": "English",    "lang": "en", "default": false }
  ],

  "seasons": [
    { "number": 1, "label": "Season 1", "episode_count": 2 }
  ],

  "episodes": [
    { "id": "ep-s1e1", "season": 1, "number": 1, "title": "Серія 1" },
    { "id": "ep-s1e2", "season": 1, "number": 2, "title": "Серія 2" }
  ]
}
```

**Епізоди — плоский список, а не вкладені в сезони.** Клієнт сам групує їх за
полем `season`. `seasons` — це лише підсумки (`label`, `episode_count`), щоб
показати «N серій» без рахунку плаского списку; епізодів там немає і бути не
повинно.

**В озвучках поле називається `label`, а не `name`.** `label` обов'язкове — без
нього запис викидається, бо в інтерфейсі нічого не показати. `lang` — код
ISO 639-1, `default` — твоя рекомендація, коли користувач нічого не обрав.
Поля `seasons` усередині озвучки в протоколі немає.

**`episodes[].id` — це твій токен, ти сам його розумієш.** Kadrbox зберігає
його дослівно і віддає назад у `/streams?id=…&season=…&episode=…`. Не намагайся
зробити його гарним — зроби стабільним. Зміниш формат — зламаються збережені
вподобання. Не вкладай у нього URL сторінки: це непрозорий ідентифікатор, а не
посилання.

## 7. `headers` — і ось де ти можеш нашкодити

```json
"streams": [
  { "url": "https://cdn.example/hls/x/index.m3u8",
    "quality": "1080p",
    "voiceover": "uk",
    "headers": { "Referer": "https://example.com/" } }
]
```

`voiceover` — це **ідентифікатор** доріжки з `voiceovers[].id` у `details`, а не
назва. Клієнт показує гравцеві саме те, що вирішив відтворити, тож назва без
ідентифікатора нічого не дає.

Дозволено **тільки** `Referer`, `User-Agent`, `Origin`.

Клієнт викине все інше, зокрема `Authorization` і `Cookie`, навіть якщо ти
попросиш. Це не свавілля — це захист користувача. Напиши в документації свого
сервера: «для токенів є окремий ендпоінт», а не «впишіть токен у headers».

`headers` діють **лише** на той `url`, який ти повернув. Не на редиректи, не на
інші хости.

---

## 8. `quality` — ніколи не вигадуй

`Quality` = те, що ти **прочитав у master-плейлисті**. Ніколи не будуй шлях
за якістю.

Реальний випадок: `/hls/1080/index.m3u8` віддає **200** з master, який вказує
на 480p. Сегменти за цим шляхом — ті самі файли, що й за правильним. Тобто
шлях, побудований за назвою релізу, дає порожнє відео й **`200` як підтвердження
успіху**. Ми на це наступили.

Якщо master немає — поверни `quality: "auto"` і не вигадуй значення.

## 9. Помилки

| Код | Коли | Що робить клієнт |
|---|---|---|
| `400` | запит кривий | показати помилку, не чистити стан |
| `404` | такого елемента/джерела немає | приховати елемент |
| `429` | ти обмежив | відступити й повторити |
| `502` | все джерела впали | показати збій сегмента |
| `503` | сервер тимчасово недоступний | показати «недоступно» |

**Ніколи не повертай `200` з порожнім `items` замість помилки.** Користувач не
зрозуміє, чи каталог порожній, чи він зламаний. Найгірше, що можна зробити —
виглядати так, ніби все працює.

Помилки — машинні рядки (`upstream_timeout`, `upstream_403`), не текст для
людини: клієнт показує своє формулювання, а твоє показує в лозці.

---

## 10. Поводь себе як гарного громадянина

Kadrbox кешує `/details`, але **не кешує `/search` і `/streams`**.

Тобто тисяча користувачів на твоєму сервері — це тисяча пошуків **наживо** і
тисяча `/streams` наживо. Якщо ти не кешуєш у себе, тебе заблокують за
тиждень.

Що варто зробити на своєму боці:
- кеш `/details` агресивно (воно незмінне)
- кеш пошук на 30–60 с
- обмежуй себе `429`, а не віддавай помилку 500

---

## 11. Anti-ban — твоя відповідальність

**Kadrbox більше ніколи не ловить бан за скрейпінг.** Він не скрейпить. Усе
anti-bot — твоє: ротація IP, резидентні проксі, кеш, темп.

Це і є причина, чому сервер каталогу існує окремо. Але нерівність
відповідальності не означає, що її можна ігнорувати: якщо тебе заблокують,
користувач не отримає нічого.

## 12. Тести

**Пиши тести проти фігур, а не проти мережі.** Мережа зміниться завтра — тест
на ній зламається без твоєї вини.

```ts
test('search returns a segment even when one source is down', async () => {
  // один адаптор кидає, другий повертає
  expect(res.segments).toHaveLength(2);
  expect(res.segments.find(s => s.id === 'broken')!.status).toBe('error');
  expect(res.status).toBe(200);          // не 502 — решта жива
});
```

Обов'язкові кейси:

- [ ] одне джерело впало, решта жива → `200`, `status: "error"` у сегмента
- [ ] усі джерела впали → `502`
- [ ] порожній результат → `200` + `status: "empty"` + `item_count: 0`
- [ ] `file://` у `url` ніколи не потрапляє у відповідь
- [ ] `item_count` дорівнює фактичному числу елементів
- [ ] `/details` віддає `episodes` **плоским** списком, а не вкладеними в `seasons`
- [ ] у кожної озвучки є `label`, а не `name`
- [ ] `catalog_id`, якщо віддаєш, стабільний між перезапусками

## 13. Чого ми навмисно не вимагаємо

Не залиш без уваги, бо спокуса велика:

**Аутентифікація не потрібна.** Kodi й Lampa працюють анонімно, і для нашої
моделі це правильно: немає акаунта, немає відповідальності, немає abuse-репортів
по нашому «кабінету». Якщо хочеш токен — це необов'язкове поле.

**Пагінація.** `next_page` — це рядок, який клієнт не розбирає. Не мисли ним
як про число.

**Кластеризація — не твоя.** Якщо користувач додасть два сервери, злиття
дублікатів робить **застосунок**. Тому повертай «як є, як знайшов» — інакше
фільтрувати дублі в тебе двічі.

---

## 14. Як користувач знаходить твій сервер

**Це нерозв'язана задача, і ми не зобов'язані її розв'язувати.** Ми не ведемо
реєстр серверів і не роздаємо жодних URL.

Практично це означає: ти або даєш посилання своїм користувачам, або
публікуєш деінде сам. Якщо вирішимо зробити реєстр — це буде окрема фаза, і
протокол для неї ще не існує.

---

## 15. Правова сторона

Kadrbox не має жодного каналу, яким роздавати твої джерела. Він не знає, які
це джерела, і не знатиме.

Це означає, що **вся** відповідальність за те, що ти віддаєш, — на тобі й на
операторі сервера. Ми технічно не причетні, і це не звільняє тебе ні від
відповідальності, ані від наслідків.

---

## 16. Ні назви сайту, ні в чому

Останнє правило, і воно не технічне.

**Назви конкретних сайтів не мають з'являтися аніде в протоколі.** Не в `app`, не
в `segment.label`, не в `catalog_id`, не в `id` елемента, не в `error`, не в
прикладах.

Це не стилістика. Застосунок показує `app` і `segment.label` користувачеві
як назву джерела, а `catalog_id` та `id` пишуться в сховище. Назва сайту,
що потрапила в ці поля, — це доказ у публічному сховищі, і рев'юєр магазину
його знайде. Тому в `contracts/` усі хости синтетичні: `catalog.example`,
`cdn.example`, `example-provider`.

`error` — машинний рядок (`upstream_timeout`, `upstream_403`), а не текст для
людини й не ім'я сайту.
