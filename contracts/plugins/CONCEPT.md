# Концепція плагінів Kadrbox

> Статус: проєкт для обговорення. Нормативний джерело — `contracts/PROTOCOL.md`.
> Цей документ пояснює **чому** так, а не перелічує поля.

---

## 1. Головне, що треба зрозуміти: у Kadrbox немає плагінів у сенсі Kodi

Kodi, Lampa і Rave встановлюють **код**. Користувач додає адресу репозиторію, завантажується JS-файл, і він виконується на пристрої. Звідси й уся їхня могутність — і вся їхня проблема: застосунок щойно завантажив і виконав чужий код.

**Kadrbox так не робить і не буде.** Застосунок ніколи не завантажує і не виконує код зі стороннього джерела. Він завантажує **дані**.

```
       KODI / LAMPA / RAVE              KADRBOX
┌──────────────────────────┐   ┌──────────────────────────┐
│ завантажує JS            │   │ ніколи не завантажує JS   │
│ виконує JS локально      │   │                          │
│ сам ходить на сайти      │   │ ходить на сервер каталогу │
│                          │   │ сервер ходить на сайти    │
│ ⇒ тор-сила на пристрої   │   │ ⇒ тор-сила на сервері     │
│ ⇒ Google Play: ні         │   │ ⇒ Google Play: так        │
└──────────────────────────┘   └──────────────────────────┘
```

Наслідок, який варто проговорити вголос: **спільнота, яка пише парсери, більше не отримує жодної аудиторії з нашого боку.** Kadrbox не є дистриб'ютором контенту і не має ані жодного каналу, яким його можна роздавати. Це не втрата — це і є модель, за якої застосунок проходить модерацію.

## 2. Три шари

```
┌─────────────────────────────────────────────────────────────┐
│ 1. ЗАСТОСУНОК (Kadrbox)                                      │
│    плеєр, пошук, сезони/епізоди, синхронізація, watch party │
│    НЕ знає жодного сайту. НЕ робить жодного парсингу.       │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTPS, JSON, за схемою contracts/
                            │ Користувач сам вводить цю адресу
┌───────────────────────────▼─────────────────────────────────┐
│ 2. СЕРВЕР КАТАЛОГУ (сторонній, не наш)                       │
│    тримає парсери, ходить на сайти, віддає нормалізований    │
│    JSON. Жодних правил щодо того, які це сайти — ми їх       │
│    не знаємо і не хочемо знати.                              │
└───────────────────────────┬─────────────────────────────────┘
                            │ тримає власних правил і ключів
┌───────────────────────────▼─────────────────────────────────┐
│ 3. АДАПТЕР                                                  │
│    код всередині сервера, який знає один конкретний сайт.     │
│   Living поза нашим репозиторієм.                            │
└─────────────────────────────────────────────────────────────┘
```

**Ми не пишемо шар 2 і шар 3.** Ми пишемо лише шар 1 і контракт між 1 і 2.

Це розподіляє відповідальність так, що кожна сторона має справжній стимул тримати свою частину в порядку:

| | Хто відповідає |
|---|---|
| Синхронізація, watch party, акаунти | ми |
| Якість коду парсерів, їхня стійкість до змін DOM | оператор сервера |
| Захист від бану за свій IP | оператор сервера |
| Відповідальність за те, які джерела його сервер віддає | оператор сервера |

## 3. Що постачається за замовчуванням

Нуль. При першому запуску у застосунку:

- локальні файли з диска
- легальні джерела (окремий вбудований модуль, `LegalDefaultsSource`)
- продовжити перегляд (з синхронізації)
- watch party
- **і явна підказка**: «Додайте URL каталогу, щоб дивитися онлайн-контент»

Жодного предустановленого URL. Ніяких назв сайтів в інтерфейсі, у логах, у тестах, у документації.

Це не скромність. Якщо ми поставимо хоча б один URL за замовчуванням, то застосунокAgain почне показувати піратський каталог, і ми повернемося рівно туди, звідки пішли.

## 4. Як виглядає підключення для користувача

Один текстове поле. Це весь UX. Образно — за Lampa.

```
Налаштування → Каталоги

  [ https://example-catalog.org                     ]
  [ Перевірити ]

  Статус: OK — протокол v1, 5 джерел, оновлено щойно
```

`Перевірити` робить `GET /status`. Якщо відповів інакше — конкретна помилка:

| Відповідь сервера | Що кажемо користувачеві |
|---|---|
| версія протоколу новіша за нашу | «Сервер новіший за застосунок. Оновіть Kadrbox або користуйтеся іншим сервером.» |
| версія старша | «Застарілий сервер. Можлива неповна поведінка.» |
| немає обов'язкового поля | «Це не сервер каталогу Kadrbox.» |
| таймаут | «Сервер не відповідає. Перевірте адресу та VPN.» |
| TLS-помилка | «Сервер не використовує HTTPS. Kadrbox вимагає HTTPS.» |

Останній рядок — не формальність: ми не будемо робити HTTP-вимкнення в Android, бо це окрема тема модерації (див. `SECURITY.md`).

## 5. Кілька каталогів

Спершу — одна адреса. Це достатньо для 95% випадків і не плутає нікого.

Але якщо користувач додав два сервери, пошук має їх об'єднати. Саме тут працює рішення **`segments[]` — масив, а не фіксовані поля**. Кожен сервер каталогу повертає свої сегменти, застосунок їх склеює:

```json
{
  "query": "величне століття",
  "took_ms": 812,
  "segments": [
    { "id": "legal-defaults", "label": "Built-in",  "provider": "legal", "status": "ok",    "item_count": 3 },
    { "id": "cat_a",          "label": "Catalog A", "provider": "cat_a", "status": "ok",    "item_count": 12 },
    { "id": "cat_b",          "label": "Catalog B", "provider": "cat_b", "status": "empty", "item_count": 0 },
    { "id": "cat_c",          "label": "Catalog C", "provider": "cat_c", "status": "error", "item_count": 0,
      "error": "upstream_timeout" }
  ],
  "items": [ ... ]
}
```

Наслідок: додавання нового сегмента **ніколи** не ламає клієнта. Тому ми й не фіксували поля під конкретні джерела — це була б та сама помилка, що й коштувала б нам версії протоколу.

`status` на сегменті **обов'язковий**, і це не формальність. Сервер зазвичай робить фан-аут на кілька джерел, і одне з них мертве — це норма, а не виняток. Без `status` у сервера лишаються два нечесні варіанти: або не повертати сегмент узагалі (і каталог виглядає порожнім), або повернути 200 зі скороченим списком (і зламане джерело виглядає як те, що просто нічого не знайшло). Застосунок показує стан по кожному сегменту й лишає решту працювати.

## 6. Ідентичність елемента

`item_id` призначає сервер каталогу. **Він не глобально унікальний.**

Тому застосунок склеїє собі складений ключ:

```
<catalog_id>:<item_id>
```

і зберігає його в історії, обраному та завантаженнях. Той самий `item_id` на двох різних серверах — це два різні фільми, і вони не мають зливатися. Тому в БД унікальність історії має бути `(user_id, catalog_id, item_id)`.

`catalog_id` сервер **може** оголосити сам у `/status`. Поле необов'язкове:
контракт вимагає рівно три поля у `Status`, і клієнт зобов'язаний прийняти
відсутність `catalog_id`. Тоді застосунок виводить ідентичність сам — з повної
базової URL-адреси, а не з хоста, бо два каталоги на одному хості мають бути
різними просторами імен.

Епізод має `ref`, який сервер розуміє сам. Застосунок зберігає `ref` **дослівно** і віддає назад без розбору.

## 7. Кеш і офлайн

Сервер каталогу може зникнути. Тому застосунок кешує:

- `/details` — добре, деталі не змінюються
- `/status` — коротко, 5 хвилин
- `/search` — **не кешуємо.** Пошук у свіжому станом і є цінністю
- `/streams` — **не кешуємо.** Посилання підписані й короткоживі

Історію перегляду зберігаємо локально завжди: користувач має бачити, що він дивився, навіть якщо сервер мертвий. Натиснути «грати» з мертвого сервера — повідомлення, а не помилка.

---

## 8. Версії

```json
GET /status
{ "protocol_version": 1, "app": "...", "capabilities": ["search","details","streams"] }
```

- **Несумісна зміна** → `protocol_version + 1`.
- Застосунок **ніколи** не падає на невідомій версії: попереджає і працює з тим, що розуміє.
- Сервери ми не супроводжуємо й не можемо оновити. Тому застосунок зобов'язаний лишати сумісним із попередньою версією так довго, як це можливо. Це не добра ввічливість — це єдина можливість.
- `capabilities` дозволяє серверу не вміти сезони, і тоді застосунок показує серії одним рівнем замість того, щоб зламатися.

## 9. Відхилені альтернативи

Записано, щоб не винаходили заново.

### JS-плагіни в WebView
**Головний недолік — Google Play.** Політика Play забороняє завантажувати та виконувати виконуваний код поза фреймворком; інтерпретований JS у WebView дозволений, але це сіра зона, коли застосунок сам завантажує та виконує скрипти. Плюс: CORS, неможливість підкласти TLS-відпечаток, питання пісочниці для довільного коду з доступом до файлової системи.

**Вердикт:** можливо колись, як окремий експериментальний режим без Google Play. Не як основа.

### Локальний sidecar-процес
**Головний недолік — знову Play.** Go-бінарник, який користувач тягне з GitHub, є нативним кодом. Плюс треба підтримувати збірки під 4 платформи й стежити, щоб нічого не зникло.

**Вердикт:** відхилено. Це те, що я сам пропонував до того, як зрозумів політику Play — записано, бо помилка була чесною й корисною.

### Ми хостимо сервер каталогу
**Головний недолік — це не розв'язує нічого.** Ми просто переносимо піратський індекс на один хоп далі: той самий домен, та сама репутація, ті самі Abuse-повідомлення. Обгортка з REST не робить це легальним.

**Вердикт:** відхичено. Наш сервер — це auth/sync/watch party. Жодного контенту.

### Єдиний «офіційний» каталог у застосунку
**Вердикт:** відхилено. Наявність одного URL за замовчуванням означає, що застосунок знову показує піратський контент.

## 10. Наслідки для магазинів

Що саме ми можемо показати на модерації:

| Питання рев'юєра | Відповідь |
|---|---|
| Чи містить застосунок парсери? | Ні. У репозиторії їх немає, CI-гейт не дає їм з'явитися |
| Чи звертається застосунок до серверів з контентом? | Ні. Лише до URL, який користувач ввів сам |
| Чи вбудовані джерела? | Ні. Нуль URL за замовчуванням |
| Чи шифрує з'єднання? | Так, HTTPS обов'язковий для каталогу |
| Чи виконує застосунок чужий код? | Ні. Тільки JSON |

Скрини для лістингу — локальні файли, watch party, легальні джерела. Жодних сторонніх обложок.

## 11. Що це означає для нас як для розробників

**Найважливіше наслідок: ми більше не тримаємо парсери, а значить більше не маємо чого ламати.** DOM стороннього сайту змінюється щотижня, і це більше не наша робота.

Це не означає, що ми не маємо роботи. Залишається:

- підтримка протоколу (semver, конформанс)
- клієнт каталогу: кеш, таймаути, деградація
- безпека: що ми дозволяємо серверу надсилати
- версії магазинів

Це роботи, які не розпадаються від чужого DOM.
