# Roadmap: джерела даних (LampaME / lme.isroot.in)

Статус документа: живий. Оновлюється в міру прийняття рішень.
Останнє оновлення: 2026-09-30.

Цей документ фіксує, які зовнішні джерела ми інтегруємо, які відхилено і
чому. Рішення ухвалені на основі **живих вимірів**, а не документації.

---

## 1. Головне: `lme.isroot.in` — це оператор, а не один сервіс

Ми інтегрували `bbe.lme.isroot.in/api/v2` і вважали це єдиною зовнішньою
залежністю. Виявилося — це екосистема з чотирма різними сервісами:

| Хост | Призначення | Стан |
|---|---|---|
| `bbe.lme.isroot.in/api/v2` | Bandera: каталог, деталі, стрими | інтегровано |
| `apx.lme.isroot.in` | універсальний проксі-шлюз | **не інтегровано, див. §2** |
| `wm.lme.isroot.in/wm` | карти якості (Movie Enhancer) | у плані |
| `wh.lme.isroot.in` | наявність перекладу / community | частково закритий, див. §4 |

Це змінює оцінку залежності: ми залежимо від **одного оператора**, а не від
одного сервісу з однією точкою відмови. Водночас різні сервіси мають різні
SLAs і різні режими доступу — див. §4.

## 2. `apx` — проксі-шлюз, ключова знахідка

### Що це

Універсальний шлюз виду:

```
https://apx.lme.isroot.in/destination/<повний URL цілі>
```

Клієнт не звертається до цільового сайту напряму. Запит йде на `apx`,
відповідь приходить з їхньої інфраструктури.

### Навіщо це нам

Це відповідь на ризик, який порушив архітектуру пошуку: якщо наш сервер
скрейпить `uakino.biz` / `eneyida.tv` / `lavakino.net` напряму, ми отримуємо
бан за наш IP, і разом з ним втрачаємо пошук для всіх користувачів.

Через `apx` наш IP ніколи не світиться перед цільовим сайтом. Поверхня для
бану переходить на оператора.

### Перевірено вживу

```
GET https://apx.lme.isroot.in/destination/https://kinobaza.com.ua/api/v1/titles?q=dune
→ HTTP 200, application/json, 16093 байт
→ {"total":44,"data":[{...}]}
```

Поля відповіді: `id`, `slug`, `name_uk`, `name_en`, `name_original`, `year`,
`rating`, `imdb_rating`, `poster_tmdb`, `poster_kinobaza`,
`has_ukr_translation`, `has_only_subtitles`, `number_of_episodes`,
`released_ua`, `released_en`.

У HTML відповіді присутній `<meta name="mitgo-verification" content="...">` —
система стеження ввімкнена. Сьогодні запити проходять, але це **стан, а не
гарантія**. Через `apx` ми знімаємо з себе цей ризик.

### Обмеження, які зафіксовані

- `apx` root → `HTTP 502`. Це не «сервіс мертвий», це endpoint-специфічна
  поведінка: шлюз не має обробника кореня.
- `apx` → `streamingdiscovery.com` → `HTTP 410 Gone`. Отже whitelist
  destination-ів існує, це **не** довільний шлюз. Перед покладанням на нього
  треба зрозуміти, що саме в whitelist.
- Відповідь `410`/`404` від шлюзу **не** означає, що ціль мертва. Треба
  відрізняти «шлюз відмовив» від «ціль не знайдена».

## 3. Kinobaza — погоджено, з однією суттєвою оговоркою

### Рішення

Прийнято. Використовується **тільки для канонічної ідентичності**, не для
відтворення.

### Що дає

У пошукових відповідях немає посилань на відео, але є `name_uk`, `name_en`,
`name_original`, `year` — саме те, чого бракувало для надійного ключа
дедуплікації. Комбінація «Kinobaza = хто це і які дублі» + «Bandera = де
грається» закриває проблему дублікатів краще, ніж Bandera сам по собі.

### ОГОВОРКА: немає зовнішніх ID

Перевірено: фільтри `?ids=`, `?slug=`, `?imdb_id=` **ігноруються** — усі
три повертають однакову відповідь (перша сторінка каталогу, `total=475180`).
Тобто Kinobaza підтримує лише фільтр `q` (+ `page`, `type`, сортування).

Наслідок: **`imdb_id` / `tmdb_id` з Kinobaza не отримати.** Дедуплікація
буде **нечіткою за назвою**, а не точною за спільним ідентифікатором.

Це суттєво. Точний ключ (`imdb_id` або `tmdb_id`) кращий за fuzzy-збіг
назв у кожному сценарії конфлікту. Тому:

- дедуплікація лишається переважно на Bandera-даних, де `sources[]` дають
  реальні джерела;
- Kinobaza використовується як **підсилення** для збагачення полів
  (`name_uk`, `year`, постер) та як додатковий сегмент пошуку;
- `cluster.go` не змінюємо, але має враховувати, що для kinobaza-сегмента
  ключ слабший, і не піднімати йому `score` вище, ніж у Bandera.

### Статус

Не реалізовано. Планується **після** стабілізації пошуку.

## 4. CommunityWatches — відкладено, є блокер

### Що дає

`GET https://wh.lme.isroot.in/v2/top` — живий, `HTTP 200`, JSON, 20 записів
виду:

```json
{"id":"tv:124364","created_at":"...","updated_at":"...","requests_count":16311}
```

Тобто спільнотний топ із лічильником популярності. Це замінило б наше
фальшиве «популярне = пошук за українським словом "фільм"».

### БЛОКЕР: ID не розрезолюються

Гіпотеза, що `id` у CommunityWatches — це те саме числове ID, що й у
Kinobaza, **не підтвердилася**. Перевірено 8 записів через три різні форми
запиту — `0/8` розпізнано.

### Причина: WH API закритий авторизацією

Усі інші шляхи `wh.lme.isroot.in` повертають:

```
HTTP 401  Іди броди
```

Тобто `/v2/top` публічний, а API доступності翻译 — під токеном. Nnightingale
якосто отримує його, принаймні з Lampa.

**Висновок:** без WH-авторизації `CommunityWatches.top` дає лише нечитабельні
ID. Тобто зараз сегмент некорисний.

### Що потрібно, щоб розблокувати

З'ясувати, як Nightingale отримує токен для `wh.lme.isroot.in`, і чи
припустимо це в нашому сценарії. Якщо токен прив'язаний до Lampa — сегмент
не беремо.

## 5. Movie Enhancer — погоджено як дизайн-референс

`MovieEnhancer.js`, 68 КБ. Хости: `api.mdblist.com`, `api.themoviedb.org`,
`api.tvmaze.com`, `apx.lme.isroot.in`, `wm.lme.isroot.in`.

Опис: «Комплексний апгрейд картки: кнопки, рейтинги, перемикач джерела,
метадані».

**Рішення: інтегрувати код не потрібно.** Це референс для хвилі 3C
(редизайн сторінки опису). Корисні патерни, які варто перенести в нашу
роботу:

- кнопки на картці без переходу в деталі
- перемикач джерела прямо на картці
- збагачення метаданих з кількох API (TMDB + TVmaze + MdbList)

`apx` тут знову фігурує — Movie Enhancer теж ходить через проксі-шлюз, а не
напряму.

## 6. Відхилено — з обґрунтуванням

| Плагін | Причина відхилення |
|---|---|
| **Tracks Probe** (`tracks.js`) | Працює через `api.shotstack.io` і надсилає **наші підписані CDN-URL** сторонньому сервісу. Animeon віддає `?expires=…&sig=…` — це наші квитки до контенту. Роздавати їх чужому хосту неприйнятно. Ендпоїт потребує ключа і POST. |
| **TS Tracks Probe** | Те саме, джерело TorrServer. |
| **IMDb Trailers** | Дублює `tmdb_service.dart`, який уже є. Додатково йде через сторонній проксі `proxy.m7-club.com`. |
| **Jacred Proxy** | `https://parserbridge.lampame.v6.rocks/` → `HTTP 502`, не працює. |
| **TraktTV, Torrent Manager, Infuse Save, Concert Torr Search** | Торрентний бекенд і клієнти — не наш профіль. |
| **GramLink, NightingaleNotifications, CommunityWatches(UI)** | Синхронізація через Telegram, сповіщення, соціальні фічі — не наш профіль зараз. |
| **TryzubTV, Hikka Anime** | Окремі українські каталоги з власним парсингом. Конкурують з тим самим, що вже дає Bandera. Додавати — значить відкривати собі ту саму поверхню для бану, яку ми щойно закрили. |

## 7. Правило, яке виникло з цього дослідження

**Перш ніж інтегрувати будь-яке нове джерело, перевіряти три речі:**

1. Чи це API чи скрайп сайту. API з документацією — беремо. Скрайп — ні,
   бо це поверхня для бану нашого IP.
2. Чи є за ним офіційний проксі-шлюз (як `apx`). Якщо є — ходимо тільки
   через нього.
3. Чи покриває він сегмент, який вже закритий Bandera. Якщо так — це
   дублювання, а не покриття.

Це правило застосовується retroactively до `uakino` / `eneyida` / `lavakino`:
вони не проходять ані пункту 1, ані пункту 2, тому залишаються мертвим
запасом у коді без участі в пошуку.
